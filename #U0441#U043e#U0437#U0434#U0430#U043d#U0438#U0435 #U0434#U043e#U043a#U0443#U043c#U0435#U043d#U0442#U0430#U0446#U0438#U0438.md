Ниже — **практическая инструкция именно для существующего репозитория без документации**, чтобы подготовить его к работе с ИИ-агентом.

Главная идея:  
**не писать документацию “из головы”, а восстановить её из кода, конфигов, скриптов и CI**.

---

# Цель

На выходе в репозитории должны появиться хотя бы:

- `AGENTS.md`
- `PROJECT_MAP.md`
- `README.md`
- `ARCHITECTURE.md`
- `TESTING.md`
- `.env.example`

Опционально, но очень полезно:

- `CONTRIBUTING.md`
- `docs/API.md` или `openapi.yaml`
- `docs/ADR/`
- `Makefile` или набор стандартных скриптов

---

# Ключевое правило

Для репозитория без документации есть 1 важное правило:

## Не выдумывать
Если что-то не подтверждено кодом, конфигами, тестами или запуском проекта:

- не писать это как факт
- писать `TODO`
- писать `UNKNOWN`
- или явно отмечать: “предположение, требует проверки”

Для ИИ-агента **неточность хуже отсутствия документации**.

---

# Общий порядок работы

Правильная последовательность такая:

1. Создать отдельную ветку под документацию
2. Провести аудит репозитория
3. Проверить, как проект запускается
4. Выделить структуру и ключевые модули
5. Выделить команды и правила проверки
6. Определить опасные зоны и generated code
7. Создать файлы документации в правильном порядке
8. Проверить документы на реальной задаче

---

# Этап 1. Создай отдельную ветку

Чтобы не мешать основной разработке:

```bash
git checkout -b docs/bootstrap-ai-agent-context
```

Если репозиторий большой, можно делать поэтапно:

- `docs/readme-bootstrap`
- `docs/project-map`
- `docs/agents-md`

Но обычно удобнее одной веткой.

---

# Этап 2. Собери факты о репозитории

Сначала нужно быстро понять, что это за проект.

## 2.1. Посмотри корень репозитория

Ищи такие файлы:

- `package.json`
- `pnpm-lock.yaml`
- `yarn.lock`
- `pyproject.toml`
- `requirements.txt`
- `Pipfile`
- `go.mod`
- `Cargo.toml`
- `pom.xml`
- `build.gradle`
- `Dockerfile`
- `docker-compose.yml`
- `Makefile`
- `.github/workflows/*`
- `helm/*`
- `terraform/*`

## 2.2. Построй дерево проекта

Например:

```bash
tree -L 3 -I 'node_modules|dist|build|coverage|.git|.next|venv|__pycache__|target'
```

Если `tree` нет:

```bash
find . -maxdepth 3 \
  -not -path '*/node_modules/*' \
  -not -path '*/.git/*' \
  -not -path '*/dist/*' \
  -not -path '*/build/*'
```

### Что нужно выписать
- основные папки
- backend/frontend/services/workers
- тесты
- миграции
- конфиги
- скрипты
- generated code

# Этап 3. Найди “источники правды”

Для репозитория без документации такие файлы становятся источниками правды:

## Для запуска
- `package.json` scripts
- `Makefile`
- `docker-compose.yml`
- `Dockerfile`
- systemd / scripts / shell scripts

## Для тестов
- `jest.config.*`
- `vitest.config.*`
- `pytest.ini`
- `tox.ini`
- `go test` через CI
- `.github/workflows/*`

## Для линтинга и форматирования
- `.eslintrc*`
- `eslint.config.*`
- `.prettierrc*`
- `ruff.toml`
- `mypy.ini`
- `golangci.yml`
- `tsconfig.json`

## Для архитектуры
- входные файлы приложения
- роутеры
- контроллеры
- сервисы
- доступ к БД
- очереди
- worker-процессы

## Для env переменных
Ищи по коду:

```bash
rg "process\.env|import\.meta\.env|os\.environ|getenv\(|ENV\[|config\." .
```

# Этап 4. Попробуй реально запустить проект

Документация без проверки запуска почти всегда получается ложной.

Нужно выяснить:

- как установить зависимости
- как запустить dev-режим
- как собрать проект
- как прогнать тесты
- как прогнать линтер
- есть ли typecheck

## Что проверить
Например:

### Node.js
```bash
npm install
npm run dev
npm run test
npm run lint
npm run build
```

### Python
```bash
pip install -r requirements.txt
pytest
ruff check .
mypy .
```

### Go
```bash
go test ./...
go build ./...
```

### Docker
```bash
docker compose up --build
```

# Этап 5. Если проект не запускается — всё равно можно документировать

Если проект старый или окружение сломано, всё равно можно создать полезную базу.

Но в документации нужно честно писать:

- “команда найдена в CI, локально не проверена”
- “предположительный способ запуска”
- “требуются секреты/внешние сервисы”
- “не удалось воспроизвести окружение”

Это всё равно лучше, чем отсутствие информации.

# Этап 6. Выяви структуру проекта

Перед созданием `PROJECT_MAP.md` нужно ответить на вопросы:

## 6.1. Где основные зоны
- где backend
- где frontend
- где shared code
- где worker/cron
- где infra
- где миграции
- где тесты

## 6.2. Где точки входа
Например:
- `src/main.ts`
- `app.py`
- `cmd/server/main.go`
- `server.js`
- `apps/web/src/main.tsx`

## 6.3. Где бизнес-логика
Очень важно отделить:
- контроллеры/роуты
- сервисы/use-cases
- доступ к БД
- модели/схемы
- внешние интеграции

## 6.4. Какие места опасны
Нужно найти:
- generated code
- vendor
- legacy-модули
- auto-generated clients
- миграции, которые нельзя редактировать задним числом
- файлы, правки в которых ломают CI/CD

# Этап 7. Создай файлы в правильном порядке

Для существующего репозитория без документации лучше создавать файлы **вот в таком порядке**:

1. `README.md`
2. `PROJECT_MAP.md`
3. `AGENTS.md`
4. `TESTING.md`
5. `ARCHITECTURE.md`
6. `.env.example`
7. `CONTRIBUTING.md`

Почему так:

- `README` — даёт основу запуска
- `PROJECT_MAP` — даёт навигацию
- `AGENTS` — уже опирается на первые два
- `TESTING` и `ARCHITECTURE` — уточняют операционку и устройство
- `.env.example` — собирается из найденных env
- `CONTRIBUTING` — уже после понимания процессов

---

# Этап 8. Как писать каждый файл

---

## 8.1. `README.md`

Это первый файл, который нужен даже раньше `AGENTS.md`.

### Задача
Объяснить:
- что за проект
- как установить
- как запустить
- как проверить

### Минимальная структура
```md
# <Project Name>

## Что это
Краткое описание проекта.

## Технологии
- ...
- ...

## Требования
- Node/Python/Go version
- Docker, если нужен

## Установка
<команды>

## Запуск
<команды>

## Тесты
<команды>

## Линт / форматирование / typecheck
<команды>

## Структура
См. PROJECT_MAP.md

## Архитектура
См. ARCHITECTURE.md
```

### Откуда брать информацию
- `package.json`
- `pyproject.toml`
- `Makefile`
- CI
- Docker config

---

## 8.2. `PROJECT_MAP.md`

Это карта проекта.

### Задача
Дать ИИ-агенту быстрый ответ на вопросы:
- где что лежит
- куда идти при типовых задачах
- что нельзя трогать
- какие модули связаны

### Что включить
1. обзор репозитория
2. структура корня
3. ключевые директории
4. entry points
5. основные модули
6. flow запроса/данных
7. тесты
8. env/config
9. опасные зоны
10. типовые сценарии изменений

### Как собирать
Не копируй всё дерево.  
Сначала выпиши только:

- важные папки
- важные файлы
- модули
- зависимости между ними

### Хорошая практика
Указывать для каждой папки:
- назначение
- можно ли редактировать
- на что влияет

---

## 8.3. `AGENTS.md`

Писать только после `README` и `PROJECT_MAP`.

### Задача
Объяснить ИИ-агенту:

- как работать в этом репозитории
- что обязательно прочитать
- что можно менять
- что нельзя менять без подтверждения
- какие проверки запускать
- как отчитываться

### Что обязательно написать
- сначала читать `README.md`, `PROJECT_MAP.md`, `ARCHITECTURE.md`, `TESTING.md`
- не менять массово код без запроса
- не трогать generated code
- не менять API/DB schema без подтверждения
- запускать тесты/линт/сборку после изменений
- обновлять docs, если меняется поведение

### Важно
`AGENTS.md` — это **не архитектурный документ**, а **правила работы агента**.

---

## 8.4. `TESTING.md`

В репозитории без документации это особенно важно, потому что тестовая стратегия обычно скрыта в CI.

### Задача
Объяснить:
- какие виды тестов есть
- где они лежат
- как их запускать
- что запускать после разных типов изменений

### Структура
```md
# TESTING.md

## Какие тесты есть
- unit
- integration
- e2e

## Где лежат
- ...

## Как запускать
- ...

## Что запускать после изменений
### Изменил UI
- ...
### Изменил API
- ...
### Изменил БД
- ...
```

### Откуда брать информацию
- названия директорий тестов
- CI
- test config files
- package scripts / pytest / go test

---

## 8.5. `ARCHITECTURE.md`

Этот файл особенно нужен, если проект старый и неочевидный.

### Задача
Объяснить:
- как устроена система
- какие модули главные
- как течёт запрос
- где source of truth
- какие ограничения уже существуют

### Что писать
Не надо рисовать “идеальную архитектуру”.  
Нужно описывать **реальную текущую архитектуру**.

### Минимум
- основные подсистемы
- поток запроса
- поток данных
- работа с БД
- внешние интеграции
- auth, если есть
- фоновые задачи
- известные ограничения/legacy

---

## 8.6. `.env.example`

Его нужно создать из реальных env переменных, найденных по коду и конфигам.

### Как собрать список
Поискать в проекте:

```bash
rg "process\.env|import\.meta\.env|os\.getenv|os\.environ|getenv\(|ENV\[|settings\." .
```

### Что включать
Только:
- названия переменных
- безопасные примерные значения
- комментарии, если нужно

### Чего не включать
- реальные токены
- реальные пароли
- production secrets

### Пример
```env
NODE_ENV=development
PORT=3000
DATABASE_URL=postgres://localhost:5432/app
REDIS_URL=redis://localhost:6379
JWT_SECRET=replace_me
```

---

## 8.7. `CONTRIBUTING.md`

Если репозиторий уже живой, этот файл полезен и людям, и ИИ.

### Что включить
- стиль веток
- как оформлять изменения
- naming conventions
- правила коммитов
- что запускать перед PR
- что нельзя смешивать в одном PR

---

# Этап 9. Что ещё желательно добавить

---

## 9.1. `docs/API.md` или `openapi.yaml`
Если в репозитории есть API.

### Как собрать без документации
Смотреть:
- роутеры
- контроллеры
- схемы валидации
- swagger decorators
- serializers
- тесты API

### Что фиксировать
- endpoint
- метод
- входные параметры
- response
- auth requirements
- коды ошибок

---

## 9.2. `docs/ADR/`
Если проект уже сложный, полезно создать хотя бы 2–3 файла с ключевыми решениями.

Например:
- почему выбрана эта БД
- почему используется конкретный auth-flow
- почему legacy-модуль не трогают
- почему генерация кода устроена именно так

Если точной истории нет — можно создать ADR как **“current-state decision record”**, то есть описание текущего решения и ограничений.

---

## 9.3. `Makefile` или стандартные команды
Если сейчас запуск делается хаотично, лучше унифицировать:

```make
install:
	<command>

dev:
	<command>

test:
	<command>

lint:
	<command>

build:
	<command>
```

Это не строго обязательно, но для ИИ-агента очень полезно.

# Этап 10. Как восстановить архитектуру из кода

Если документации нет, архитектуру нужно извлекать вручную.

## Смотри в таком порядке

### 1. Точка входа
Найди файл, где стартует приложение.

### 2. Роутинг
Найди:
- router
- controller
- handlers

### 3. Бизнес-логика
Найди:
- service
- use case
- manager
- domain

### 4. Доступ к данным
Найди:
- repository
- models
- ORM
- SQL queries

### 5. Внешние интеграции
Найди:
- HTTP clients
- queue producers/consumers
- email/s3/payment adapters

### 6. Фоновые процессы
Найди:
- workers
- jobs
- schedulers
- cron

# Этап 11. Как восстановить тестовую стратегию

Если нет `TESTING.md`, смотри:

## По именам папок
- `tests/`
- `__tests__/`
- `integration/`
- `e2e/`
- `spec/`

## По CI
В workflow часто лучше всего видно:
- какие тесты реально запускаются
- в каком порядке
- какие env нужны
- какие сервисы поднимаются

## По package scripts / task runner
Например:
- `test`
- `test:unit`
- `test:e2e`
- `lint`
- `typecheck`

# Этап 12. Как определить dangerous zones

Это особенно важно для `AGENTS.md` и `PROJECT_MAP.md`.

Нужно явно отметить:

## Не редактировать вручную
- generated clients
- generated types
- `dist/`
- `build/`
- `coverage/`
- vendored code

## Редактировать только осознанно
- миграции
- docker/infra
- deployment manifests
- auth modules
- billing modules
- legacy code
- shared contracts

## Проверять особенно внимательно
- DB schema
- API response shape
- event formats
- public interfaces libraries

# Этап 13. Практический шаблон процесса

Ниже — самый рабочий процесс для репозитория без документации.

---

## Шаг 1. Инвентаризация

Собери в черновик:

- стек
- package manager
- команды
- структура папок
- точки входа
- тестовые папки
- env переменные
- CI workflow
- dangerous zones

Можно в простой заметке или временном `docs/_audit.md`.

---

## Шаг 2. Создай `README.md`
Сначала только проверенные вещи:
- что это
- как установить
- как запустить
- как тестировать

Если что-то не проверено — пометь это.

---

## Шаг 3. Создай `PROJECT_MAP.md`
Сделай короткую карту:
- папки
- entry points
- модули
- flow
- опасные зоны

---

## Шаг 4. Создай `AGENTS.md`
На основе уже собранной информации зафиксируй:
- порядок чтения файлов
- правила изменений
- запреты
- обязательные проверки

---

## Шаг 5. Создай `TESTING.md`
Собери из CI и конфигов:
- какие тесты есть
- как запускать
- какие запускать по типу изменения

---

## Шаг 6. Создай `ARCHITECTURE.md`
Кратко опиши реальную структуру приложения.

---

## Шаг 7. Создай `.env.example`
На основе реальных переменных окружения.

---

## Шаг 8. Протестируй на задаче
Например:

Если по документам сразу понятно:
- куда идти
- что менять
- какие тесты запускать

значит набор файлов хороший.

# Этап 14. Готовая структура, которую стоит получить

```txt
/
├─ AGENTS.md
├─ README.md
├─ PROJECT_MAP.md
├─ ARCHITECTURE.md

│  └─ ADR/

```

Если не хочется разводить много файлов, минимально:

```txt
/
├─ AGENTS.md
├─ README.md
├─ PROJECT_MAP.md

```

# Этап 15. Критерии качества

Документация считается достаточно хорошей, если новый ИИ-агент может ответить без просмотра всего репозитория на 7 вопросов:

1. Что это за проект?
2. Как его запустить?
3. Где основная бизнес-логика?
4. Где тесты?
5. Какие команды запускать после изменений?
6. Какие зоны нельзя трогать без согласования?
7. Что нужно менять при типичной задаче?

Если ответы размытые — документацию надо доработать.

# Этап 16. Что НЕ делать

## Не копировать старый `AGENTS.md`
Потому что:
- команды будут чужими
- ограничения — нерелевантными
- пути — несуществующими

## Не писать “идеальную архитектуру”
Нужна реальная текущая архитектура, даже если она некрасивая.

## Не вставлять полное дерево репозитория
Это шум.  
Нужна карта, а не дамп.

## Не придумывать env переменные
Только то, что реально найдено в коде/конфигах.

## Не делать `AGENTS.md` из общих лозунгов
Типа:
- “пиши хороший код”
- “следуй best practices”

Это бесполезно. Нужны конкретные правила именно этого репозитория.

# Этап 18. Рекомендуемый состав `AGENTS.md` для старого репозитория

Для существующего undocumented-репозитория в `AGENTS.md` обязательно должны быть такие блоки:

- какие файлы читать сначала
- где искать основную логику
- что считается source of truth
- что не трогать
- какие команды запускать
- когда спрашивать человека
- как оформлять итог отчёта

# Этап 19. Очень важная практика: помечай уровень уверенности

При создании документации полезно помечать информацию так:

- `Confirmed` — проверено запуском/кодом/CI
- `Inferred` — логически выведено из структуры
- `Unverified` — найдено, но не проверено
- `TODO` — требуется уточнение

Это особенно полезно в первом проходе по старому репозиторию.

Пример:

```md
## Запуск
Confirmed:
- `npm run dev` запускает локальный сервер

Unverified:
- `docker compose up` присутствует, но локально не проверялся
```
